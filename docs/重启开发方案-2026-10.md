### G. 模型厂商管理（新增，2026-10-11 用户要求）

目标：默认使用 DeepSeek，同时管理端能随时切换厂商和模型、做自定义配置。这样既能满足客户自带模型的需求，也能在 DeepSeek 成本上涨时一键切走。

现状：只有一组配置（地址/密钥/模型），请求路径写死为 `{baseUrl}/v1/chat/completions`，temperature 也写死。智谱、豆包方舟、通义等路径不同的厂商无法接入。

实施说明（2026-10-12 完成）：表名定为 `llm_profiles`，一个档案 = 地址 + 模型 + 参数（同一厂商的不同模型建多个档案）。调用层用 pi，路径规则是“地址填到 /v1 这一级，系统拼 /chat/completions”，可覆盖国内主流厂商和 NewAPI；如遇到不符合这个规则的网关再在适配层处理。协议目前只开放 OpenAI 兼容 Chat Completions。

| # | 改造内容 |
|---|---|
| G1 ✅ | **多配置档案**：新增 `llm_providers` 表，每个档案包含名称、厂商类型、Base URL、完整 Chat 路径（可改）、API Key（加密存储、界面打码）、模型名、自定义请求头、额外请求体 JSON（如关闭思考、`response_format` 等）、超时、启停。可以同时保存多个档案 |
| G2 ✅ | **厂商预置模板**：DeepSeek（默认）、通义千问、智谱 GLM、豆包/火山方舟、Kimi、硅基流动、OpenAI 兼容自定义。选好模板自动带出地址、路径和推荐模型，管理员只需填 Key |
| G3 ✅ | **按用途分别指定模型**：买家对话（重首字速度）/ 导演评估 / 六维评分 / 话术与邮件生成，各自可选不同档案和模型、不同 temperature 和 max_tokens。辅助任务可以用更便宜的模型降成本 |
| G4 ✅ | **连通性测试**：保存前一键测试，返回首字耗时、输出速度和报错原文；不通过则不允许设为生效档案 |
| G5 ✅ | **热切换与回退**：切换后立即生效、不用重启，并写审计日志；可配置备用档案，主档案连续报错时自动切到备用，同时告警 |
| G6 ✅ | **计量与成本**：每个档案可录入单价（每百万 tokens 输入/输出价），按档案和用途统计 tokens 与费用；额度提醒改为按金额或 tokens 计算，覆盖语音 |
| G7 ✅ | 语音服务同样做成可配置档案（先支持豆包，接口抽象预留其他厂商） |

### H. 前端设计大升级（新增，2026-10-11 用户要求）

### J. Agent 底座重构（2026-10-11 评估）

结论：现有“演员（买家）+ 导演 + 评分”三角色架构方向正确，**业务编排不推倒重来，也不引入 LangChain 等编排框架**（延续 D-01）；**底层 LLM 调用改用 pi**（与 AIGC 平台共用，D-18）。但工程实现还停留在“能跑”的阶段，要在 P2 和模型网关一起重构成规范的 Agent 底座。

| # | 现状问题 | 重构内容 |
|---|---|---|
| J1 ✅ | 所有 LLM 调用共用一个 `complete()`，temperature 写死，没有按用途区分 | 统一调用层**改用 pi（@earendil-works/pi-ai，锁 0.82.1，决策 D-18）**，替换自研 fetch 适配器；按用途（买家对话/导演/评分/话术）路由到不同模型档案，配置档案映射为 pi Model，extraBody 经 onPayload 注入，与 G 节合并实现 |

### K. 数据全部存云端（2026-10-11 核查）

结论：架构本身是“云端为中心”，账号、任务、会话、消息、订单、评分、邮件、语音和图片文件都存在云端 PostgreSQL 和文件卷里，客户端不存业务数据。但核查发现**有 4 类数据只存在客户端本机**，必须迁到云端。学校机房学生常换机器，很多机房还装了还原卡，本机数据重启就会丢。

| # | 只存在本机的数据 | 处理 |
|---|---|---|
| K1 ✅ | 差评回复记录（`cecs.reviewReplies.*`）——属于学生的实训成果 | 新建表存云端，教师端可查看 |
| K2 ✅ | 邮件草稿（`cecs.mailDrafts.*`） | 存云端，换机器后可以接着写 |
| K3 ✅ | 邮件已读状态（`cecs.mailRead.*`） | 存云端 |
| K4 ✅ | 教师指导通知的已读状态 | 存云端 |
| — | 界面偏好（栏宽、自动翻译开关）、登录令牌 | 可以留在本机；令牌在 Electron 中改用系统加密存储（safeStorage） |

另外，云端数据的安全和留存也要补齐：
- 备份目录挂卷，定时备份同时推送到对象存储（OSS），满足 3 年服务期的数据安全。
- 明确数据保留策略：会话和评分数据保留整个服务期，可按学期导出归档。

### L. 后台任务可靠性（2026-10-12 架构评审）

结论：200 账号**不需要拆独立 Worker，也不引入任务队列或 Redis**。系统的负载主要是等模型返回，单个 API 进程扛得住；上游（Flow API / DeepSeek）也支撑 50–80 个并发，用户确认没有问题，所以对话和导演保持直接调用，评分也不设并发上限（评分只在会话结束时触发一次，实际并发不高）。

真正的问题是：导演、六维评分、买家评价、邮件回信、验收测试都是在请求里 `void xxx().catch(log)` 发出去就不管了，**API 一重启（发版、崩溃、开发时改代码）正在跑的任务就丢了**，没有重试，也没有补救入口。2026-10-12 已经实际发生过：验收测试跑到 52/100 时，另一个会话改了 server.ts，开发环境热重启，测试中断，状态一直停在“运行中”，挡住了下一次测试。

**2026-10-21 已完成 L1–L4**（迁移 042，API 测试 152 个全绿），和原方案的出入：
- L1 补漏每 3 分钟一次（启动后 30 秒先跑一次），只捡结束 5 分钟以上、24 小时以内的；每次评分含进程内重试 2 次（等 5 秒、20 秒），`conversations.assess_attempts` 记跑了几次，满 3 次不再自动补，进系统总览告警，管理员点“重新评分”。买家留评跑完记 `conversations.review_done_at`。“评分中”在学生我的记录、教师回放与评分列表顶上显示，试满次数仍失败的显示“暂未评分”。“应该有评分”的判断统一用 `lifecycle.ts` 的 `SCORE_DUE_SQL`，教师端“未完成、不计分”也改用它（原来学生说满 3 轮、评分失败的会被误列进去）。
- L2 观察员同一会话串行：评估期间又来的轮次记一笔，评完按最新对话补评一次；学生发言计数用 SQL 原子自增；观察员和催促写 state 都走 `updateSessionState`（行锁里读最新值再合并字段，走势数组按最新值追加）。
- L3 只做了熔断按“档案 + 用途”计数；“评分和买家对话默认分配不同档案”是配置建议，没改默认值。
- L4 启动时把停在“运行中”的验收标成 `interrupted`，系统总览性能验收旁显示“上次中断 37/100”，可以直接重新运行。

| # | 问题 | 处理 |
|---|---|---|
| L1 | 评分、买家评价随 API 重启丢失，失败了也不重试；学生的任务成绩会一直空着，下课集中结束会话时最容易撞上 | **定时补漏，不建任务表**：API 启动时和每隔几分钟扫描一次“已结束、属于任务、结束超过 2 分钟、但还没有评分”的会话并重新评分；买家评价同理（已结束、未生成评价）；评分失败时在进程内退避重试 1–2 次，最终失败留给下一轮扫描；管理端加“重新评分”按钮兜底；排队和评分期间，学生端“我的记录”和教师端显示“评分中”，不显示空白或 0 分。`assessments.conversation_id` 已有唯一约束、写入是 `on conflict do nothing`，重复触发只多调一次模型，不会写出两条成绩。邮件回信是按概率触发的，分不清“没触发”和“丢了”，不补 |
| L2 | 导演竞态：学生回得快时，同一会话会有两次导演调用同时在跑；`director.ts` 最后整块覆盖 `conversations.state`，后写的覆盖先写的，`studentTurns` 计数也会算错 | 同一会话的导演串行执行（上一次没跑完就跳过本轮或排在后面）；写 state 改为按字段合并，计数用原子自增 |
| L3 | 熔断只按档案计数（`llm/gateway.ts`）：评分和对话共用同一档案时，评分连续失败 3 次会把买家对话也熔断 5 分钟 | 熔断改为按“档案 + 用途”计数；评分和买家对话默认分配不同档案 |
| L4 | 验收测试的运行状态存在 `app_settings.acceptance_run`，API 重启后永远停在“运行中”，再点运行会返回 409 | API 启动时把停在“运行中”的状态改为“已中断”，记录中断时已完成的次数；管理端显示中断原因，允许重新运行 |

架构评审提出、待用户拍板的建议（2026-10-12）：
- **客户端改为“外壳 + 从服务器加载页面”**：现在前端打包在安装包里，每次改前端都要靠自动更新。学校机房的还原卡会在重启后把程序和它更新下来的新版本一起还原，200 台同时下载安装包也很占服务器带宽。改成从服务器加载后，前端发布即生效，外壳很少需要更新。会改变 R 阶段的发版方案。
- **买家提示词按“固定在前、变化在后”排列**：导演每轮更新的情绪、记忆、指令现在夹在 system 段中间，导致历史对话部分命不中上下文缓存。挪到最后一条后，可以降低费用和首字耗时。
- **备份推送到对象存储 + 故障推送到企业微信/钉钉群**：管理端已有告警条（E5），但没人打开管理端时不会有人知道。
- **上线前办 ICP 备案**：国内服务器用域名提供网页服务必须备案，要提前一两周办。
