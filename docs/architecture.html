1. 概览

交付形态
Windows 客户端（学生/教师）+ 云端管理端（浏览器）
规模与服务期
200 账号 · 3 年服务期
技术栈
React + Vite · Fastify + TypeScript · PostgreSQL 16 · Electron
AI 服务
LLM：经团队总网关 Flow API 调 DeepSeek，可多厂商切换 · 语音：豆包 TTS/ASR
代码仓库
github.com/tangda13/kefu-agent（main）
规模
28 张表 · 23 个迁移 · 约 80 个接口

三端共用一套 React 前端代码，按登录角色渲染不同导航；学生端/教师端由 Electron 打包为 Windows 安装包，管理端由云端 nginx 以网页形式提供。所有业务数据、AI 调用和密钥都在云端 API，客户端不持有任何密钥。

核心产品原则：实训是幕后逻辑。学生端的沉浸层（客服工作台、订单、评价、邮件）必须像真实的客服软件，不出现“实训、轮次、画像”等字样；任务大厅和我的记录属于学习管理层，可以直呼任务和成绩。

2. 部署拓扑（目标形态）

正式服务器待功能完成后购买（独立服务器、单独部署）。在此之前用本机或临时环境联调；客户端里的服务地址和更新源地址都做成可配置。

5. 核心业务链路

5.1 任务到会话

  1. 教师新建任务：班级、业务环节、场景、画像随机规则（persona_rule）、交互模式、限时、开放/截止时间、评分权重 → tasks + task_classes。
  2. 学生的任务进度 task_progress 置为待办；工作台把任务伪装成“未分配新客进线”。
  3. 学生接入：POST /v1/conversations 校验开放时间 → 按 persona_rule 从启用的画像模板中组合画像（domain composePersonaWithRule）→ 按场景生成订单、物流、评价（generateOrderForScenario）；售前场景没有订单，改为从在售商品里给买家挑一个“感兴趣的商品”写进画像快照。
  4. 买家主动开场：POST :id/opening（SSE），开场会引用订单号和物流状态。

5.2 一轮买家对话

  1. 学生发送消息（可连发；2 秒打字检测窗口结束后统一触发）→ POST :id/reply。
  2. 组装提示词（prompts/buyer.ts）：买家人设（每轮重注入防漂移）+ 场景剧本（目标、隐藏信息、情绪触发点、让步底线、结束条件）+ 订单或感兴趣商品 + 导演状态（情绪、阶段、记忆、下一轮指令）+ 历史（按约 12000 字符预算从最近往前截取，至少保留 6 条；更早的事实由导演备忘录承接）。
  3. 经模型网关按“买家对话”用途调用（gateway.stream("dialogue")），主档案出错且尚未出字时自动换备用档案；SSE 推给客户端；服务端解析 ||| 拆成 1–3 条短消息，识别 [END_OF_SERVICE] 结束标记。
  4. 消息落库 conversation_messages；首字耗时（从服务端收到请求时算起）、输出速度落库 conversation_metrics（验收依据）；tokens 与费用落库 llm_usage。
  5. 异步：导演（director.ts）按“导演评估”用途调用，JSON 模式 + zod 校验（不合格带错误重试 1 次，仍失败保留上一轮状态），更新本轮得分、满意度、情绪、剧情阶段、事实记忆 → conversations.state。可设置每 N 轮学生发言运行一次以降本。
  6. 买家输出结束标记 → 服务端关闭会话 → 六维评分（assessment.ts，“六维评分”用途）：读全量对话（超过 24000 字符先分段摘要），把违规词命中和导演逐轮得分作为客观依据一起交给模型 → assessments（记录提示词版本、所用模型和依据）；任务成绩 = 该任务下所有已评会话的加权均分 → task_progress.score。自由练习会话不评分。
P2 已完成 Agent 底座（方案 J 节）：所有 LLM 调用经 llm/gateway.ts，按四种用途（买家对话 / 导演评估 / 六维评分 / 话术与生成）路由；提示词集中在 prompts/ 并带版本号；结构化输出统一 completeJson；场景剧本可由教师在「场景配置 → 场景库」编辑；Agent 评测集 dev.cmd eval。保留“演员 + 导演 + 评分”三角色编排，不引入编排框架；底层调用用 pi（@earendil-works/pi-ai 0.82.1）。

5.3 订单、邮件、评价中的 AI 辅助

订单页的催付、物流同步、差评回复，以及邮件页的 AI 辅助写信，都由“话术与生成”用途的模型实时生成三个版本（JSON 模式 + 校验），学生选择、二次编辑后发送到关联会话或邮件。邮件提交时服务端用 content_terms 词库复核违规用语；营销邮件按客户类型概率触发买家 AI 回信（mail_replies）。

5.4 教师监控与介入

实训跟踪页每 8 秒轮询 teacher/tracking（参数要求 ≤10 秒），买家消息超过 3 分钟未回会预警；教师可对任意会话发送指导，学生端通过 student/guidance 轮询，在顶栏铃铛里收到通知。

7. 账号与权限

角色入口数据范围实现
学生客户端 · 学生登录页签仅本人数据所有学生接口查询都带 student_id = 本人
教师客户端 · 教师登录页签自己是班主任或被授权任课的班级teacherOwnsClass / scopedStudentsSql
管理员浏览器 · 管理端全部也可调用所有教师接口

登录态：access token 为 HS256 JWT，有效期 15 分钟（ACCESS_TOKEN_TTL）；refresh token 14 天，数据库只存哈希，每次刷新轮换。密码用 scrypt 加盐。改密、重置、停用（学生和教师）时吊销该用户全部 refresh token。页签与账号角色不符时拒绝登录并提示。

鉴权守卫：令牌只证明身份；每次请求再查一次账号状态和待改密标记（10 秒缓存，停用/改密/重置时立即失效）。停用的账号立即 401 ACCOUNT_DISABLED；待改密账号除改密和 /me 外一律 403 PASSWORD_CHANGE_REQUIRED。

登录限流：同一账号 15 分钟内连续输错 5 次锁 15 分钟；同一 IP 15 分钟内失败 100 次锁 15 分钟（机房共用出口 IP，阈值放宽）。返回 429 LOGIN_LOCKED，写审计 auth.locked。教师/管理员重置密码会解锁。部署在 nginx 后需 TRUST_PROXY=true，nginx 用 $remote_addr 覆盖 X-Forwarded-For。

找回密码：学生 → 教师重置；教师 → 管理员在「账号与权限」重置；管理员 → 服务器执行 pnpm reset-password admin（容器内 docker compose exec api pnpm reset-password admin）。

后台任务

  • 导演 Agent：买家回复后异步执行（每 N 轮学生发言一次，管理端可调）。
  • 六维评分：会话关闭后异步执行。
  • 买家邮件回信：邮件提交后异步执行。
  • 定时备份：server.ts 每 10 分钟检查一次备份计划（按容器时区；Docker 中缺 pg_dump，待修复）。
以上异步任务都在 API 进程内执行，请求里发出去就不再跟踪，API 重启时正在跑的任务会丢失。规划 开发方案 L 节（P5 前做）：评分和买家评价定时补漏 + 失败重试 + 管理端“重新评分”；导演按会话串行、state 按字段合并；熔断按“档案 + 用途”计数；启动时复位中断的验收测试。不拆独立 Worker、不引入任务队列：200 账号的负载主要是等模型返回，单进程足够；以后要部署多台或出现耗 CPU 的任务时再拆。

本地开发

端口：API 8787 · 前端 5288（strictPort）· 数据库容器 cecs-pg:5434。启动：根目录 dev.cmd（服务 + 学生/教师两个独立登录的客户端）、admin.cmd（浏览器管理端）。第一个启动服务的窗口是托管窗口，API 与前端日志合并显示，Ctrl+C 或关窗即全部停止；之后的入口只开客户端/浏览器后退出。dev.cmd status / restart api / logs / stop / test / eval。日志在 .devrun/logs。验证：pnpm build && pnpm test，前端类型检查用 cd apps/portal && npx tsc -b --force。详细运维见 skill kefu-weihu。
